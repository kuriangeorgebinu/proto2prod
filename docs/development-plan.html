Development plan

How we get from today's foundation to an MVP that takes the sample app's source code and returns a verified, production-ready pull/merge request with Terraform, CI/CD and OIDC access to AWS.

Principle: everything is proven on the sample app

examples/notes-app is a small Next.js + Postgres prototype with 16 planted production flaws, listed in a scoring key the agents never see. Every milestone ends with a test run against it, so progress is measured, not guessed.

Milestones

Weeks assume one developer working full-time with AI assistance.

M1

Foundation and analyzer

DoneWeek 0
  • Design, stack-adapter model (Next.js + generic fallback)
  • Shared contract schemas and validator
  • Sample app with 16 planted flaws and scoring key
  • Analyzer agent: stack detection, flaw scanners, profile + contract
  • GitHub and GitLab project detection for OIDC trust
M2

Infrastructure generation

NextWeeks 1–2
  • Tested Terraform module library: network, ECR, ECS service, RDS, CloudFront, Secrets Manager
  • Architecture agent: picks a tier, writes the decision record, estimates cost with Infracost
  • Terraform agent: composes modules from the contract; pinned providers, S3 remote state
  • Dockerfile generation from the stack adapter
Done when: the sample app's generated Terraform passes terraform validate and Checkov, and the cost estimate fits its budget.
M3

CI/CD and OIDC trust

PlannedWeeks 3–4
  • One-click bootstrap stack (CloudFormation) for GitHub and GitLab: OIDC provider, scoped deploy role, Terraform state bucket and lock table
  • CI/CD agent: generates .gitlab-ci.yml or GitHub Actions — build, test, scan, plan, deploy staging, gated production
  • Trust-policy checks: exact project and branch, no wildcards
Done when: the sample app's pipeline, running in a test GitLab project and a test GitHub repo, authenticates to a sandbox AWS account via OIDC and runs terraform plan with no stored keys.
M4

Orchestration, review and proof

PlannedWeeks 4–6
  • Orchestrator: runs workers in parallel on separate branches; integrator merges against the contract
  • Reviewers: security (Checkov, gitleaks, dependency audit), cost, policy; rework loop (max 3 rounds)
  • Test deploy to a throwaway environment, smoke tests, guaranteed teardown
Done when: one command takes the sample app to a passing throwaway deploy on AWS, with review evidence attached.
M5

Refactor agent

PlannedWeeks 6–8
  • LLM-driven fixes for the Next.js adapter: server-side auth, password hashing, stateless sessions, shared DB client, migrations, health check, validation, dependency upgrades
  • Code reviewer: tests, type-check and lint must pass; no unrelated changes
Done when: at least 14 of the 16 sample-app flaws are fixed and verified by the reviewers, and the app still works end to end.
M6

Product and beta

PlannedWeeks 8–10
  • GitHub App and GitLab integration: connect a project, open the pull/merge request
  • Web dashboard: start a run, watch agents, see findings, cost and evidence
  • Pricing, sign-up, docs; 5–10 beta users with real prototypes
Done when: a beta user goes from repo to approved pull/merge request without our help.

After the MVP: more stack adapters (FastAPI/Django, Express, Rails), an optional console assistant for the few account-setup tasks AWS has no API for, and more architecture tiers.

Main risks

RiskHow we handle it
AI-written Terraform is unreliableAgents only compose our tested modules; validate, Checkov and a real deploy before anyone sees it.
Refactors break the appCode reviewer runs the app's tests; smoke tests in the throwaway deploy; every change is in one reviewable pull/merge request.
Overly broad OIDC trustTrust pinned to exact project and branch; security reviewer rejects wildcards.
Surprise AWS bills from test deploysTTL tags, guaranteed teardown, cleanup job, budget alerts on the sandbox account.
Competitors (Opsera VibeShift, Pulumi Neo)Differentiate on verification: independent review and proof-by-deploy, in the customer's own account and repo.
