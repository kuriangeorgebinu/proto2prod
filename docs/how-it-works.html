proto2prod

From prototype to production on AWS, verified

Point proto2prod at your app's source code. A team of AI agents turns it into a production-ready app with Terraform, a CI/CD pipeline and secure OIDC access to your AWS account, delivered as one pull or merge request.

  • Dockerfile and Terraform for the whole stack
  • CI/CD pipeline that deploys via OIDC
  • Architecture summary and monthly cost
  • Review results and a passing test deploy

The journey, step by step

You do three things: connect the repo, click once in AWS, and approve the result. Agents do everything else, and different agents check it before you see it.

  1. Connect your repo You

    Link the GitHub or GitLab project, pick a traffic tier and budget. proto2prod only gets read access plus the right to open a pull/merge request.

  2. Create the AWS trust in one click You

    You open a "Launch stack" link while signed in to AWS and press Create. The CloudFormation stack sets up the OIDC trust, a scoped deploy role and Terraform state storage. No passwords or keys are shared.

  3. Analyze Agent

    The analyzer detects the stack, finds production problems (hard-coded secrets, missing auth checks, in-memory sessions…) and writes a shared contract: the exact names every other agent must use.

  4. Build in parallel Agents

    Four workers run at the same time, each on its own branch, all following the contract.

  5. Review and rework Agents

    Independent reviewers check security, cost, code and policy. Problems go back to the worker that made them, for up to three rounds.

  6. Prove it works Agent

    The result is deployed to a throwaway environment, smoke-tested, and torn down. Logs and results are attached as evidence.

  7. Approve and ship You CI/CD

    You review one pull/merge request. Once merged, your pipeline deploys to staging automatically; production waits for your approval.

How your pipeline reaches AWS without keys (OIDC)

Your CI/CD never stores AWS access keys. On each run, it proves who it is with a short-lived signed token and AWS hands back temporary credentials that expire within an hour.

→

→
Terraform + deployrun with those credentials

The trust only accepts tokens from your project and branch. For GitLab it looks like this (GitHub uses repo:owner/repo:ref:refs/heads/main instead):

"Condition": {
  "StringEquals": { "gitlab.com:aud": "https://gitlab.com" },
  "StringLike":   { "gitlab.com:sub": "project_path:acme/notes-app:ref_type:branch:ref:main" }
}

Self-managed GitLab works the same way with your GitLab URL, as long as AWS can reach it over the internet.

The pipeline it sets up

On every pull/merge request: build, test, scan dependencies, the container and Terraform, then show the terraform plan.

On merge to main: deploy to staging automatically, run migrations once, smoke-test.

Production: same artifact, released only after a human approves.

Guarantees

  • No long-lived keysCI uses OIDC; nothing permanent to leak.
  • Never touches production aloneProduction deploys always need your approval.
  • Checked by someone elseReviewers never grade their own work.
  • Proven before you see itA real throwaway deploy must pass first.
